# Seedance 成本快查表应用建议（2026-10-21）

本轮为文档与代码核查，没有修改采购价、零售价或数据库，不调用收费生成。

## 结论

快查表用于 Token 用量估算、最低用量下限和离线报价回归，不直接替代本账号的采购单价，也不应用到 ext/req 独立按次通道。

来源：

- [Seedance 价格快查表](https://docs.toapis.com/docs/cn/api-reference/videos/seedance/pricing)
- [账号生效价格与实际费用](https://docs.toapis.com/docs/cn/api-reference/account/pricing)

## 已核实的本地代码

- `app/services/toapis_catalog_expansion.py`：已区分按次、按秒、Token采购口径；Token型号零售仍按秒，其成本估值来自“低至每秒”价格。
- `app/services/product_video_service.py`：报价传入输入视频与输出视频秒数合计。
- `app/services/pricing_service.py`：匹配档位后使用固定每秒估值，并没有本快查表按比例、时长划分的最低Token表。因此部分短输入场景存在低估风险；这是源码判断，未读取当前数据库验证所有实际售价。
- `app/integrations/toapis/video_client.py` 与 `app/tasks/product_video_tasks.py`：已读取并保存任务的 billing、usage，能够作为实际成本对账的基础。保存原始数据不等于已完成财务成本结算和毛利对账。

## 一个风险实例

快查表中 Seedance 2.5，720p、16:9、24fps，输入视频2秒、输出5秒：最低194400 Token，表中采购费率42元/百万Token。

- 按该公开费率精算参考成本：194400 × 42 / 1000000 = 8.1648元（网页展示8.16元）。
- 当前初始化估值：0.7513 × (2 + 5) = 5.2591元，约低估35.6%。
- 若采用该公开费率、60%毛利与100平台积分/元，基于未先取整的参考成本计算需向上取整为2042积分；这只是算例，不是本账号已经确认的采购价或已经生效的售价。

因此不能仅用“低至每秒价格×合计秒数”保证目标毛利，也不能把最低Token值当作最大用量保证。

## 推荐落地

1. 采购费率：复用现有账号价格目录刷新，按精确模型ID、分组、清晰度、有无视频输入、计费单位匹配。账号价已含折扣/分组倍率，不重复乘；USD转人民币保留汇率快照。人工锁价继续受保护。
2. Token估算：按型号、清晰度、比例、帧率、输出时长及服务端探测的输入视频时长估算，套用含输入视频时对应的最低Token用量。缺映射或文档不完整时拒绝自动核价或要求确认，不盲目线性外推。最低值不是上限，可根据真实账单偏差增加可配置安全余量。
3. 单位隔离：Token模型以估算Token×采购单价预估；按次模型继续按输出时长阶梯×请求数，不能混入输入视频秒数或最低Token表；真正按秒模型沿用真实按秒规则。
4. 售价：本阶段建议用户确认固定报价，平台完成后只校正内部采购成本/毛利，不静默追加扣点。若未来采用预冻结、多退少补，必须单独设计并让用户事前确认上限，不能通过本轮修估价顺带启用。
5. 实际对账：优先 billing.status=settled 的 cost_usd；usage.billed_tokens 是计费量，不能无条件拿模型报告的 total_tokens 替代。pending 或缺失保留待核实，refunded按已确认净费用零处理。任务最终账单与创建时采购/售价快照关联，不用今日价格重算历史。
6. 运营展示：管理端分开“估算成本／已确认成本／报价毛利／实际毛利／偏差”。用户端只展示真实规格与本次平台报价，不下发采购费率或内部配方。

## 验证建议

- 对快查表按型号、清晰度、比例与时长版本化，记录来源、抓取时间、校验结果；文档重复行按键去重，冲突值阻止导入。
- 离线测试覆盖2秒输入+5秒输出的下限、长输入、多参考视频、各比例、480/720/1080/4K的实际支持组合。
- 维持10/15/16/30秒按次边界、不乘时长、人工锁价保护和旧订单快照测试。
- 对接实际账单的 settled/pending/refunded/缺失状态，验证多结果聚合、幂等入账、失败退款，不把模拟结果写成真实收费验收。
