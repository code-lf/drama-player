# 多视频批次执行基础验收（2026-10-24）

本轮不修改短剧或启用旧画布。批次确认执行仍未开放，以下是主链路基础，不代表完整交付。

## 已实现

1. `ProductVideoService.create_task` 新增仅服务端可用的 `transaction_only` 路径，继续调用原签名/方案许可/价格/素材/模型及扣点校验，但不自行提交或派发。客户端不能通过 HTTP 指定该参数。仅接受单条产出、稳定请求号、已签名独立运行许可和固定素材，不接受临时上传图片。
2. 批次服务 `stage_authorized_tasks` 将全部子任务、素材绑定、原账务流水置于同一事务；数量 1～12，独立请求号不得重复，实际费用之和必须等于授权总额。任一条失败整体回滚，不出现前一条扣费后第二条校验失败的半提交。
3. 批次事务避开模板种子隐式提交，沿用核价时已准备模板。任务保存持久化 `batch_dispatch_pending` 标记。
4. 新批次 Worker 采用 PostgreSQL 会话 advisory lock 互斥，重复消息不进入采购；成功、失败、取消及待核对状态不被重复消息复活。历史独立任务保留原路径。
5. 采购前写入独立条目的提交意图；若网络异常、返回无编号、或受理编号落库失败导致状态未知，标记 `needs_review`，不自动重购或退款。已持久化受理编号沿用原查询恢复链路。此安全门不等于已经开发全部对账管理操作。
6. 待派发服务只处理已落库且带批次标记的 queued 子任务。Redis 失败保留待执行记录，重复投递使用同一业务任务编号；近期已发送记录暂不重复投，超过五分钟仍排队可补投，执行互斥和采购意图阻止重复采购。running/终态/未知态及历史独立任务不被扫描。
7. 明确使用新 `batch-video` 队列，防止旧消费者未加载保护代码却消费新批次。已添加受控恢复任务及路由，但本轮未启动该新消费者，未派发真实付费任务，未重启已有生成 Worker。
