## 0.2276元/秒的准确来源

从官网公开前端JS确认价格页使用`POST /api/sku/quote/batch`。本轮不带Cookie、不带API Key只读实查三组参数成功，记录见`.codex-runtime/toapis-website-quote-check-20261021.json`。

Mini、480p、10秒、无输入视频返回：

```text
estimated_second_price.output_unit_price = 0.03252 （美元/秒）
description = 基于线上 usage.total_tokens P75 的每秒预估价；
              预授权另加20%安全余量，最终按实际total_tokens结算
billing = false （这个秒价不是实际计费单位，不是费用为零）
```

页面每秒人民币 = 0.03252×7 = 0.22764，显示四位小数为0.2276。
10秒 = 0.3252美元；按页面200 ToAPIs积分/美元折算为65.04积分。这里可精确复现截图，而不是拿四舍五入后的0.2276再反推。

P75是历史样本75分位，意味着它既不是模型固定Token/秒，更不是保证上限；视频素材与分辨率改变时要重新核对。预授权20%余量不是最终一定扣费，也不是我们的毛利率。

## 能否直接获取他们算好的钱或积分

| 来源 | 生成前能拿到什么 | 边界 |
|---|---|---|
| 文档化`GET /v1/pricing` | 账号生效的美元每秒/每次/每百万Token费率，以及可用附加价字段 | 不返回某次任务总价、不锁价、不能把单位价当总价 |
| 官网`/api/sku/quote/batch` | 本轮Wan720p10秒直接给4.2元，Banana1K给0.14元；Token型号给单位价和P75估算秒价 | 官网使用但未列入公开API文档；不保证与我们的API Key账号折扣/分组相同，需官方确认支持、鉴权、限流及稳定性，不能直接作为生产扣费依据 |
| 任务`billing` | settled时可读cost_usd及已确认ToAPIs credits | 生成后数据；pending/缺失不能记零，refunded才是已确认净费零 |
| 任务`usage` | billed_tokens、requests、output_seconds等实际计费量 | billed_tokens优先于随意选total_tokens，缺失不倒推造量 |

特别注意官网Mini响应的`estimated_price_type=unit_price`：`estimated_price=3.285714`是每百万Token美元单价，绝不是10秒任务总价；每秒估值要读取独立的estimated_second_price字段。本轮官网报价并未返回预计credits字段，不应臆造统一credits响应。

## 建议的价格体系

### 1. 将费率、估算与实际成本分开

- 保留原始采购目录快照、精确型号/通道/分组、所有价格条件、charge_type/price_basis/unit、币种、汇率及来源时间，失败保留最后可信快照但明确过期。
- 每模型维护target_gross_margin、费用安全余量、sync_mode（自动/人工锁价）、零售价策略（手动确认/受限自动）、生效版本。安全余量与利润率不能混为一个字段。
- 按秒：输出秒成本=账号unit_price×汇率；只在目录明确有输入附加费时另计，不把所有模型都按输入+输出秒数收费。
- 按次：每请求成本=unit_price×汇率；每张/每次需遵守requests、n与batch_size的真实语义；时长阶梯按输出时长选择，不乘秒数。
- Token视频：先按分辨率、比例、帧率、输出时长、服务端探测的参考视频时长估算Token，再应用最低Token下限与安全余量，乘账号Token费率；内部每秒估值=该场景预估总成本/输出秒数，不是全模型唯一常数。P75可作预算参照，不能替代最低用量规则或上限控制。
- Token图片：文本输入、图片输入、缓存、图片输出分别估算并匹配image_token_prices，不把text_input单价当整张图片价格；无法安全估算时不要自动出固定低价。
- 搜索等工具费、输入图片免费额度、minimum_charge_usd、分时/分组条件应单列；未完整识别条件不得自动覆盖生产价。现有刷新匹配器只处理部分条件，跨模型自动化前需先加强。
- 建议零售价=ceil(预估总成本×100/(1-target_gross_margin))；按单位取整还是按整单取整必须统一，UI与扣费共用。内部已确认成本优先billingsettled，再算实际毛利。

### 2. 手动与定时刷新

- 手动：抓取目录→验证完整性/分页/单位/条件→展示采购差异→按各模型已保存毛利生成售价预览→显式确认应用。人工锁价默认跳过，需要单独授权解除，不顺带破坏ext人工阶梯。
- 定时：复用现有Celery Beat与独立任务，建议先只同步采购快照和异常报告，售价保持手动确认。后续再为逐模型授权的自动调价增加涨跌阈值/最大变化比例/最低毛利/过期价/缺价处理。
- 单实例锁、防并发刷新/调价、任务审计、失败重试、最后成功时间及人工锁价保护必需；启用前还须确认Beat进程实际运行。后台配置频率和时区，不使用当前聊天自动化代替平台任务。

### 3. 跨模型批量毛利

- 在模型列表增加多选；统一毛利或逐模型毛利两种输入，预览汇总全部受影响档位及异常项，支持仅保存目标毛利而不立即改价。
- 应用时按模型稳定顺序加锁，指纹覆盖采购版本、旧售价、汇率和毛利。建议默认整批原子提交；跳过项明确列出，不能一部分失败却提示全部完成。
- 报价确认卡与新任务固化版本；旧订单、预扣和生成中任务永不因今日目录刷新被追溯改价。用户已确认后不静默追加扣点。

## 推荐顺序

先完善条件匹配与Token估算→成本/实际账单归账→跨模型批量毛利预览与确认→定时仅采购同步→最后才评估受控自动售价。由于本轮主要要求核实与方案，本轮没有启用定时任务、批量改旧毛利或替换现有Token报价算法。
